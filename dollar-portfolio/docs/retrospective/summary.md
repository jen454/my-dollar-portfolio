# 종합 회고

> CS / 운영·마케팅 측면의 잘된 점과 개선 여지를 정리한다.

---

## 잘된 점

**CS**
- 순수 함수 + 단위 테스트로 핵심 계산 로직(가중평균, 손익)을 안전하게 검증할 수 있는 구조를 만들었다.
- Storage 2계층 폴백(SDK → localStorage)으로 저장 실패 시에도 데이터 소실을 방어했다.
- 1시간 캐시로 한국수출입은행 OpenAPI의 일일 호출 제한을 실질적으로 피할 수 있다.
- 스키마 버전(`version: 1`)을 초기부터 명시해 향후 데이터 마이그레이션 경로를 열어뒀다.

**운영/마케팅**
- 토스 미니앱 플랫폼으로 별도 마케팅 없이 잠재 사용자 접근성을 확보했다.
- 면책 고지와 기능 범위 제한으로 금융 규제 리스크를 관리했다.
- WebView 방식으로 앱 스토어 심사 없이 즉시 배포가 가능하다.
- 데이터 축적 구조가 자연스러운 리텐션 동인이 된다.

---

## 개선 여지

**CS**

| 문제 | 내용 | 방향 |
|------|------|------|
| 비영업일 루프 API 비용 | 최대 5번의 연속 API 호출이 발생할 수 있다 | 마지막 성공한 `rateBaseDate`를 캐시에 저장해 다음 조회 시 불필요한 날짜는 건너뜀 |
| 기기 변경 시 데이터 이전 불가 | localStorage는 기기/앱 재설치 시 소실 | JSON 내보내기/가져오기 기능 추가 |
| 자정 직후 불필요한 API 호출 | 캐시 히트 조건에 날짜 비교가 포함되어 자정이 지나면 무조건 재조회 | 비영업일이면 다음 영업일 오전까지 캐시 유지 |

**운영/마케팅**

| 문제 | 내용 | 방향 |
|------|------|------|
| 온보딩 UX 미흡 | 첫 사용자가 서비스 가치를 바로 파악하기 어렵다 | 첫 진입 시 가치 설명 + 거래 추가 유도 플로우 |
| 데이터 이식성 없음 | 백업/복원 불가로 신뢰 장벽이 생긴다 | CSV 내보내기 최소 구현 |
| 외부 바이럴 불가 | 토스 정책상 외부 링크 불가, 플랫폼 밖 마케팅 채널이 없다 | 앱 내 공유(카카오톡 등 텍스트 공유)로 보완 가능성 검토 |
| 플랫폼 단일 의존 | 토스 정책/SDK 변경에 취약 | 독립 웹앱 버전 병행 운영 검토 |

## 핵심 교훈

1. **좁은 가치 제안이 오히려 강점이다.** "달러 평균 환전단가 계산기"라는 명확한 한 줄 설명이 사용자 진입 장벽을 낮춘다.
2. **플랫폼 유통은 양날의 검이다.** 초기 배포 비용을 낮춰주지만 독립적인 성장 전략을 막는다.
3. **데이터가 곧 리텐션이다.** 기록이 쌓일수록 이탈이 어려워지는 구조는 의도적으로 설계해야 한다.
4. **금융 계산기에서 면책 고지는 기능이다.** 규제 대응을 사후 처리가 아니라 설계 단계에서 포함하면 기능 범위도 자연스럽게 정해진다.
